## Описание проекта

Консольная клиент-серверная модель регулируемого перекрёстка на C17 для Linux. Автомобили и пешеходы прибывают с разных направлений, ожидают в ограниченных очередях и пересекают общую зону по сигналам светофора.

Сервер владеет моделью и переключает фазы; рабочие клиенты создают прибытия своих направлений; наблюдатели получают согласованный снимок и дальнейшие события. При `N` направлениях и `M` наблюдателях работают `1 + N + M` независимых процессов, до 64 соединений на сервере.

## Особенности реализации

* **Обмен по TCP/IPv4:** три независимых приложения, IP и порт через CLI, запуск на одном или нескольких компьютерах.
* **Общая модель:** FIFO очередей, матрица конфликтов, ограниченная вместимость и точная цель с учётом активных проездов.
* **Управление движением:** fixed/adaptive, приоритет экстренного транспорта без обгона FIFO и пешеходный запрос.
* **Комплексное наблюдение:** несколько наблюдателей, актуальный снимок при подключении и общий поток событий.
* **Согласованная остановка:** первая причина STOP, заморозка статистики и общий срок отправки итогов клиентам.
* **Дескрипторный ввод-вывод:** неблокирующий select, ограниченные буферы, обработка частичных операций и отключений.

## Сборка и запуск

Нужны CMake 3.20+ и компилятор C17; Python 3.8+ нужен только тестам.

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build --parallel
ctest --test-dir build --output-on-failure
# Либо обычная сборка и все проверки одной командой:
./tests/run.sh none
```

Санитайзеры включаются в отдельной сборке:

```bash
cmake -S . -B build-asan -DCMAKE_BUILD_TYPE=Debug -DENABLE_SANITIZERS=ON
cmake --build build-asan --parallel
ctest --test-dir build-asan --output-on-failure
# Либо:
./tests/run.sh asan
```

Для трёх приложений без Python:

```bash
cmake -S . -B build-release -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=OFF
cmake --build build-release --parallel
```

Предупреждения: `-Wall -Wextra -Wpedantic -Wconversion -Wshadow`.
ASan/UBSan не объединяется с TSan; TSan не нужен для этой однопоточной программы.

### Ручной независимый запуск

Каждую команду запустить в отдельном терминале. Для `minimal.conf` нужны оба направления A и P.
Наблюдатель необязателен; чтобы записать историю с начала, подключить его до последнего рабочего клиента.

```bash
mkdir -p results
./build/crossroad_server 127.0.0.1 3939 data/minimal.conf
./build/crossroad_observer 127.0.0.1 3939 results/watch-01.log
./build/crossroad_client 127.0.0.1 3939 A
./build/crossroad_client 127.0.0.1 3939 P
```

Интерфейс:

```text
crossroad_server BIND_IP PORT CONFIG
crossroad_client SERVER_IP PORT STREAM
crossroad_observer SERVER_IP PORT [NEW_LOG]
```

IP — числовой IPv4; порт — 1–65535. Observer принимает только новый путь LOG,
чтобы не перезаписать существующий файл. При повторном запуске выбрать новое имя.
Наблюдателей можно подключать, отключать и запускать снова; каждому выдаётся актуальный снимок.

Для `demo.conf` запустить пять клиентов N, S, E, W, P. Контроллер начинает отсчёт,
когда впервые зарегистрированы все направления. На это отводится 10 секунд.
Observer не участвует в барьере. Клиент может стартовать раньше сервера: connect повторяется до 10 секунд.

### На нескольких компьютерах

На серверном Linux-хосте указать его адрес интерфейса, например `192.168.1.10`:

```bash
./build/crossroad_server 192.168.1.10 3939 data/minimal.conf
```

На другом Linux-хосте выполнить:

```bash
./build/crossroad_observer 192.168.1.10 3939 watch-remote.log
./build/crossroad_client 192.168.1.10 3939 A
```

Клиент P можно запустить на любом из этих хостов с тем же адресом сервера.
Это пример адреса: заменить его фактическим. TCP-порт должен быть доступен между хостами.
Конфиг читает только сервер; общая файловая система не нужна. Бинарники собираются для ОС/архитектуры каждого хоста.

## Конфигурация

Примеры: `data/minimal.conf`, `data/compatible.conf`, `data/emergency.conf`, `data/demo.conf`.

```text
ticks 100
tick_ms 20
min_green 2
max_green 4
clearance 1
stream A car north straight 2 1 1000
stream P pedestrian east walk 2 1 1000
phase cars A
phase pedestrians P
```

`stream NAME KIND DIRECTION MANEUVER CAPACITY CROSSING_TICKS RATE` задаёт полосу
с одним манёвром либо пешеходный переход. KIND — car/pedestrian, DIRECTION —
north/east/south/west, MANEUVER — straight/right/left для автомобилей, walk для пешеходов.
RATE — 0–1000 (вероятность генерации на такт в тысячных долях).
`phase NAME STREAM...` задаёт совместимые направления. По умолчанию все конфликтуют;
`conflict A B 0` симметрично разрешает совместимость, `1` запрещает. Собственный конфликт
отключать нельзя. Все направления должны входить хотя бы в одну фазу.

| Параметр | По умолчанию | Диапазон |
|---|---:|---|
| ticks / target | 120 / 0 | 0–1000000000; 0 отключает предел |
| seed | 39 | 0–4294967295 |
| strategy | adaptive | fixed / adaptive |
| min_green / max_green | 4 / 10 | 1–10000, min ≤ max |
| clearance | 2 | 1–10000 тактов |
| priority | 1 | 0 / 1 |
| emergency_rate | 20 | 0–1000 |
| tick_ms / delay_ms | 1 / 0 | 1–60000 / 0–60000 мс |

До 16 направлений/фаз; ёмкость — 1–64 ожидающих, активный участник отдельно;
проезд — 1–1000 тактов, не больше max_green. Имя — 1–31 ASCII-буква, цифра, `_` или `-`.
Объявления направлений предшествуют ссылкам на них. Числа десятичные, без знаков/суффиксов.
Комментарии начинаются с `#`; CRLF и отсутствие последнего LF допустимы. Повтор скалярного
параметра заменяет значение. Размер файла до 16384 байт, NUL и переполнение времени запрещены.

ticks и target одновременно нулевые задают неограниченную модель до ModelStop.
Иначе остановка — по периоду или точной цели с резервированием активных участников.
Цель без периода и без возможных прибытий даёт UNREACHABLE. Итоги сохраняют баланс
`прибыло = прошло + отказов + ожидают + в_зоне`; задержки считаются в тактах.
Генератор SplitMix64 на клиенте адресуется по seed, индексу направления и такту сервера. Пропущенные такты не воспроизводятся задним числом. Одинаковый seed не гарантирует одинакового сетевого расписания или итоговых счётчиков.
delay_ms определяет частоту событий состояния, не время проезда.

## Время и процессы

Все процессы однопоточные; сокеты обслуживаются неблокирующим `select`. Нет общей памяти, именованных IPC, дочерних процессов сервера и сторонних C-библиотек.

### Интерфейс модели

- `ConfigLoad(cfg, path)` читает и проверяет обычный текстовый файл, закрывает свой fd.
- `ModelInit(model, cfg, callback, context)` копирует проверенную конфигурацию.
- `ModelArrive(model, stream, emergency, now)` ставит участника в очередь; возвращает
  false при отказе, неверном направлении/признаке экстренности или остановке.
  Полная очередь регистрирует прибытие и отказ; неверный запрос участника не создаёт.
- `ModelAdvance(model, now)` завершает созревшие проезды, обслуживает контроллер
  и допускает головы FIFO. Сервер должен вызывать его до и после пачки прибытий,
  даже если сетевых запросов нет.
- `ModelStop(model, reason, signo)` фиксирует первую причину, публикует итоги
  и замораживает состояние. Проезд, прерванный остановкой, остаётся в зоне.
- `ModelSnapshot(model, snapshot)` копирует состояние и статистику без генерации событий.

`now` — относительное время в наносекундах от начала моделирования. Оно не должно
уменьшаться; нарушение переводит модель в ERROR. Самостоятельно часы модель не читает.
При редких вызовах просроченные выходы выполняются на текущем времени; новые фазы
и защитный интервал не проигрываются задним числом. Все участники и очереди принадлежат
Model, callback синхронный и не должен изменять модель. Строка callback действительна
только во время вызова; номер события и время передаются отдельно, stream=-1 — общее событие.
NULL callback допустим.

GREEN допускает совместимые направления; DRAIN закрывает новые въезды, сохраняя
разрешение начатых проездов; CLEARANCE начинается после освобождения зоны.
Fixed обходит фазы циклически. Adaptive выбирает старейшую голову очереди, затем
наибольшую сумму длин, при равенстве — циклический порядок. Экстренность влияет на
выбор фазы, но не меняет FIFO и не отменяет минимальное зелёное время или интервал.

### Обмен и отображение

Сервер печатает общие события контроллера; рабочий клиент — события своего направления и ACK.
Observer получает META с именами/параметрами, согласованный снимок и все дальнейшие EVENT.
По его выводу можно следить за всей системой без остальных консолей.

```text
HELLO 1 FLOW A
WELCOME index seed rate kind emergency_rate
TICK tick
ARRIVE tick emergency
ACK tick id accepted

HELLO 1 WATCH
WELCOME WATCH
META STREAM index name kind direction maneuver capacity crossing_ticks conflict_mask
META PHASE index name mask
META TIMING tick_ms min_green max_green clearance
SNAP_BEGIN seq time_ns
STATE phase state signals active passed stop
FLOW index queued head_id active_id leave_at arrived passed refused wait_sum wait_max peak
SNAP_END seq
EVENT seq time_ns stream description
STOP reason status
```

STATE: 0 INITIAL, 1 GREEN, 2 DRAIN, 3 CLEARANCE. Kind: 0 автомобиль, 1 пешеход.
Направления north/east/south/west имеют коды 0–3; манёвры straight/right/left/walk — 0–3.
Имена фаз и направлений связаны с индексами через META. Маска использует бит с номером направления.
Время EVENT/SNAP_BEGIN и leave_at — относительные наносекунды сервера; задержки wait_sum/wait_max — в тактах.
В EVENT `stream=-1` означает общее событие; description — русское предметное сообщение.
Порядок полей FLOW одинаков для всех направлений. Среднюю задержку можно получить как wait_sum/passed.

TCP-кадры — строки UTF-8 с LF, до 1024 байт вместе с LF. Команды/числа — ASCII;
NUL, лишние поля и неверные числа отклоняются. Разделители команд — одиночные пробелы, регистр значим.
Нет передачи padding структур и зависимости от порядка байтов машины.
На peer выделены ограниченные буферы; одновременно допускается до 64 соединений суммарно.
Медленный peer при переполнении очереди отключается, другие продолжают работу.
PING/PONG поддерживает связь; отсутствие входящих сообщений 5 секунд закрывает соединение.

## Завершение и журнал

`ticks` ограничивает период, `target` — число завершённых участников; оба 0 означают работу до сигнала.
Сервер останавливается также при SIGINT/SIGTERM, ошибке или недостижимой цели без периода и без интенсивностей.
Первый STOP замораживает модель; незавершённый проезд остаётся в зоне. Итоги включают число прошедших,
отказы, оставшиеся очереди, задержки и пик очереди, сохраняя баланс:

```text
прибыло = прошло + отказов + ожидают + в_зоне
```

После итогов сервер рассылает STOP и сбрасывает очереди в пределах одного общего срока 2 секунды.
Причины: 1 период, 2 цель, 3 сигнал, 4 ошибка, 5 недостижимая цель.
Коды сервера: 0 штатно, 1 ошибка, 2 неверный CLI/конфиг, 3 недостижимая цель, 128+signal — сигнал.
Клиенты после корректного STOP печатают причину/код сервера и выходят с 0; ошибка связи/вывода даёт 1,
неверный CLI — 2, собственный сигнал — 128+signal.

SIGINT/SIGTERM рабочего клиента отключает только его. Уже принятые участники остаются на сервере:
проезд завершается, очередь обслуживается, а повторно запущенный клиент создаёт новые прибытия.
Принятый номер такта хранится сервером дольше соединения, поэтому повтор не создаёт второго участника.
После SIGKILL сервера STOP доставить невозможно: клиенты завершаются по EOF/ошибке/heartbeat.
Состояние после перезапуска самого сервера не сохраняется; авторизации и шифрования протокол не предоставляет.

EOF не отменяет уже поставленный ответ: сначала сбрасывается выходная очередь.
Незавершённая входная строка при EOF считается ошибкой. Ошибка одного peer не завершает сервер.

## Проверка

CTest содержит `model`, `protocol_buffers`, `protocol`, `scenarios`, `observers`,
`lifecycle`, `stress`. Независимый `check_log.py` восстанавливает очереди, фазы,
разрешения, сроки и итоговый баланс по событиям; он обнаруживает намеренные подмены
срока проезда, конфликта и счётчиков. Проверяются неверный ввод/команды, FIFO и
каталог вместо конфига, фрагментация TCP, EOF/half-close, частичная запись,
лимит fd/соединений, закрытый/заблокированный stdout, сохранность существующего LOG,
снимки и переподключения, сигналы, heartbeat без FIN, повтор ARRIVE и общий STOP deadline.

Stress повторяет 20 сессий с разными ролями, рабочими клиентами и наблюдателями.
Harness собирает свои процессы; число его открытых fd после прогона не увеличивается.
Повторные запуски используют тот же порт внутри сценария; TCP TIME_WAIT не считается утечкой.
